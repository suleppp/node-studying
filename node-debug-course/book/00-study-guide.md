# 学习说明：怎样把这套内容真正学会

你不是来“读完一些 Node.js 知识”的。你要完成一次能力变化：从看到报错就猜代码，变成能准确描述进程、执行位置、调用路径和数据第一次偏离的位置，最终像工作中的开发者一样交付复现、证据、修复和回归。

因此，这本书不能像词典一样随便翻。第一章回答“谁在运行”，第四章才能回答“当前函数从哪里来”；先理解当前栈帧，第八章才能理解 Debug Console 为什么能看到局部变量；先理解模块缓存、Promise 和缓存读写，第十三章才有可能真正调试分层服务。完整依赖关系见 [全书学习路线](learning-path.md)。

## 1. 这门课训练的不是按钮记忆

调试的核心工作是构建并修正一个“程序当前状态”的模型。每次暂停时，你至少要能回答四个问题：

1. 当前暂停在哪个进程？
2. 这个进程接下来要执行哪段代码？
3. 当前选中的栈帧里，哪些变量可见，它们分别是什么状态？
4. 如果继续，控制流会去哪里，哪些状态可能改变？

如果不能回答，不要急着按 Continue。先看 Call Stack、Variables 和源代码，把预测写下来，再执行一步验证。调试能力来自“预测—观察—修正”的循环。

## 2. 环境准备

在集成终端运行：

```bash
node --version
npm --version
code --version
```

`code` 命令不可用不影响课程；只要能打开 VS Code 即可。建议使用仍受支持的 Node.js LTS 版本。课程示例只使用 Node.js 内置能力。

打开整个 `node-debug-course` 文件夹，而不是只打开某个 `.js` 文件。这样 VS Code 才能发现 `.vscode/launch.json`，相对路径也有稳定的工作目录。

## 3. 每章的固定学习动作

每章至少做四遍：

1. **不调试运行**：先知道正常输出和外部现象。
2. **预测**：在纸上写下你认为会经过的函数、变量变化和输出顺序。
3. **断点验证**：一次只验证一个问题，不要漫无目的地连续 Step Into。
4. **复述**：不用原文，向一个不存在的同学解释“为什么”。说不清就是还没有掌握。

建议为每个问题使用以下记录模板：

```text
现象：我实际看到了什么？
期望：我本来认为会发生什么？
差异：最小的不同是什么？
假设：哪个机制可以解释这个差异？
证据：变量、调用栈、日志或最小实验怎样支持/否定假设？
结论：根因是什么？
回归：怎样证明修改没有破坏其他路径？
```

每一章还会出现四种固定学习动作：

- **承接**：说明本章使用了前面哪个模型；如果那部分说不清，应先回去补课。
- **纸上推演**：在运行代码前预测状态。没有预测，调试就会退化成看热闹。
- **动手验证**：用最少断点或命令验证预测。
- **交接到下一章**：指出当前模型还解释不了什么，下一章正是为了解决这个缺口。

阅读正文不算完成。你必须留下预测、观察和复述三个产物。

## 4. 黄色箭头的第一条纪律

本书默认把 VS Code 的当前行理解为“调试器下一步准备执行的位置”。不同暂停原因和优化情况会让源代码映射不够直观，因此它不是“这一整行已经完成”的保证。

每次暂停都用这句话自问：

> 当前行执行前，哪些副作用已经发生；执行后，又会新增哪些副作用？

## 5. 推荐节奏

- 每次 30～50 分钟；
- 一次只学一节机制；
- 阅读不超过一半时间，另一半必须动手；
- 第一阶段没有过关前，不急着研究复杂框架；
- 每完成一个阶段，隔一天重新做该阶段的最后一个实验。

如果每周只能安排四次、每次约 40 分钟，可以使用八周路线：

| 周次 | 内容 | 本周必须留下的产物 |
|---|---|---|
| 1 | 第 1～3 章 | 进程图、三行表达式求值顺序 |
| 2 | 第 4～5 章 | 手绘调用栈、第一阶段口述录音/文字 |
| 3 | 第 6～9 章 | 三断点同步故障记录 |
| 4 | 第 10～11 章 | 模块依赖图、缓存四项证据 |
| 5 | 第 12 章 | await 前后时间线与 async stack 对照 |
| 6 | 第 13 章 | 冷读/热读完整边界图 |
| 7 | 第 14～17 章 | 进程树、安全操作单、假设账本 |
| 8 | 第 18～19 章 | 工作工单示范复盘与独立结业交付 |

时间少时可以减少同一天的阅读量，但不要跳过预测、实验或阶段门槛。压缩练习会让“看过很多”替代“真正会用”。

## 6. 如何使用答案

`labs/` 中的程序包含刻意设计的故障。先完成以下动作再看 `answers/`：

1. 复现并保存输入与完整输出；
2. 明确哪个结果错了，而不只说“程序有 bug”；
3. 找到错误值第一次出现的位置；
4. 至少排除一个看似合理但错误的假设；
5. 写出最小修复和一个回归用例。

## 7. 课程中的简化模型

教材会先使用足够准确、可以指导调试的模型，再补充边界。例如把“V8 执行 JavaScript”作为第一层模型是合适的，但 Node.js 还涉及 C++、libuv、操作系统、模块加载器和内置绑定。简化不等于虚构：每次简化都会标明它能解释什么、不能解释什么。

## 8. 什么时候才允许进入下一章

不要用“我大概懂了”作为标准。满足以下三项才继续：

1. 不看正文，用自己的话回答章末问题；
2. 在实验中预测至少三个暂停点的状态，并且能解释预测错误的原因；
3. 能说出本章结论在下一章中将被怎样使用。

如果只是某个术语记不住，可以查术语表；如果无法解释因果关系，应重做本章实验。

## 9. 学习文档与代码文档的区别

代码文档告诉你函数参数是什么；学习文档必须改变你的思考顺序。本书中的代码只是显微镜下的样本，不是主角。真正要掌握的是：面对从未见过的代码，也知道先确认哪个进程、在哪个边界观察什么状态、怎样提出可以被否定的假设。

所以不要抄代码。每次改动实验前，先写下“我为什么改、改完应观察到什么”。当你能在陌生项目重复这套过程时，课程才真正结束。
