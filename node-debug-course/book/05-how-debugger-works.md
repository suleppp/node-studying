# 第五章：调试器怎样暂停程序

## 承接前四章：调试器没有创造这些状态

进程、绑定、表达式步骤和调用栈在没有 VS Code 时就已经存在。调试器的工作不是创造一个“调试版世界”，而是连接目标进程，请求它在可执行位置暂停，并把当前栈帧和可达状态翻译成界面。

这是第一阶段最后一章。前四章让你知道应该观察什么，本章解释观察通道从哪里来。学完后，你应该能区分 VS Code 客户端与被调试 Node 进程，区分 launch 与 attach，并能系统排查断点未绑定，而不是重复点击红点。

### 纸上推演

假设 Node 服务已在终端运行，VS Code 采用 attach 连接。点击 Stop 后，你预测服务会继续还是退出？再假设改为 launch，答案是否一样？先写下预测，读完 5.2 后修正。

## 5.1 调试器、被调试进程与协议

调试时至少有两个角色：

- **被调试进程（debuggee）**：真正运行 `app.js` 的 Node.js 进程；
- **调试器客户端**：VS Code 的 JavaScript 调试器，负责显示界面并发送命令。

Node.js 可启用 V8 Inspector。调试器通过调试协议连接，设置断点、请求暂停、读取栈帧、求值表达式，再把结果显示为 Call Stack、Variables 和 Debug Console。

```text
VS Code 调试界面
  │ 设置断点 / 继续 / 单步 / 求值
  ▼
JavaScript 调试器 ←→ Inspector 协议 ←→ Node.js + V8
                                      │
                                      └─ 正在执行 app.js 的进程
```

因此，Variables 不是 VS Code 猜出来的静态文本；它是从当前被调试进程、当前暂停状态、当前所选栈帧中读取的运行时信息。

## 5.2 `launch` 与 `attach`

两种最基本的调试关系：

**Launch**：VS Code 负责创建 Node 进程，天然知道程序、参数和连接方式。停止调试通常会终止它启动的被调试程序。

**Attach**：Node 进程已经由终端、npm、进程管理器或容器启动，VS Code 再连接过去。停止调试通常只是断开调试器，目标进程可以继续运行。

看到断点不命中时，先确认：VS Code 连接的 PID 是否就是处理当前请求的 PID。真实项目经常有父进程、worker、热重载子进程或多个副本。

## 5.3 `--inspect`、`--inspect-wait` 与 `--inspect-brk`

```bash
node --inspect app.js
node --inspect-wait app.js
node --inspect-brk app.js
```

- `--inspect` 开放调试连接，但代码会立即开始执行；调试器连上前的快速启动代码可能已经错过。
- `--inspect-wait` 等待调试器连接后才开始执行。
- `--inspect-brk` 在调试器连上后，于用户脚本开始处暂停。

默认 Inspector 地址通常只绑定本机回环地址和 9229 端口。不要把调试端口随意暴露到公网；连接者可以在进程上下文中求值代码，这近似于拥有该进程的执行权限。

## 5.4 断点究竟暂停什么

断点不是“冻结一行文本”，而是让调试引擎在对应的可执行位置暂停目标线程的 JavaScript 执行。当暂停发生时：

- 当前 JavaScript 不再向前执行；
- 同一个事件循环线程上的其他 JavaScript 回调也不能继续；
- 调试器可以检查活动栈帧和可达对象；
- 操作系统、其他进程和某些后台线程不一定一起暂停；
- 外部世界仍可能变化，例如远端服务超时、客户端断开。

所以在生产或共享环境停很久可能造成请求堆积、锁超时或健康检查失败。暂停不是无成本的观察。

## 5.5 为什么断点会变灰或移动

源代码行不一定有可绑定的执行位置。空行、纯注释、某些声明结构可能没有独立停点。调试器会验证断点；无法绑定时可能显示为空心/灰色，或移动到邻近的可执行位置。

其他常见原因：

- 当前运行的是另一个同名文件；
- 文件还未加载；
- TypeScript/Babel 的 source map 不正确；
- 实际进程没有连接到当前调试会话；
- 代码路径没有经过此处；
- 热重载产生了新进程或旧代码；
- `skipFiles` 使单步跳过某些文件（显式断点通常仍可命中）。

断点不命中时不要反复点击红点。依次验证进程、绝对文件路径、代码版本、模块是否加载、控制流是否到达。

## 5.6 `debugger;` 语句

```js
function calculate(input) {
  debugger;
  return input * 2;
}
```

当有调试器连接并启用时，执行 `debugger;` 会请求暂停。没有调试器时，它通常不会产生可见效果。它适合快速证明“路径是否到达”和在动态代码中制造停点，但提交前通常应移除，避免把调试意图永久留在业务代码里。

## 5.7 暂停原因

调试器可能因不同原因暂停：

- 命中普通/条件/命中次数断点；
- 执行 `debugger;`；
- 用户点击 Pause；
- Step Into/Over/Out 到达下一个位置；
- 配置为在已捕获或未捕获异常处暂停；
- 进程启动时 `stopOnEntry`/`--inspect-brk`。

先看暂停原因，再解释当前行。异常暂停时，箭头常指向“抛出错误的位置”，而不是一条尚未开始的普通语句。

## 5.8 第一阶段总实验

使用根目录 `app.js`：

1. 在 `const result = add(10, 20)` 下断点；
2. 预测暂停时模块作用域中 `result` 的状态；
3. Step Into 进入 `add`，画出两个活动帧；
4. 在 Call Stack 点击调用者帧，观察源位置和变量；
5. 回到顶部帧，Step Out；
6. 验证 `result` 何时变为 `30`。

## 第一阶段过关标准

你能不用“代码就是从上到下跑”这一句含糊概括，而是准确说出：进程是谁创建的、入口怎样加载、当前源位置、表达式求值顺序、活动调用帧和返回后的继续位置。

## 进入第二阶段前的口述考试

打开根目录 `app.js`，不启动调试器，指着 `const result = add(10, 20)` 口述完整过程：哪个进程执行、右侧怎样求值、进入函数后栈里有哪些帧、返回值送到哪里、何时初始化 `result`。如果这段话仍只能说成“进去算完再出来”，请重做第三、四章。

第二阶段不会再重新讲这些原理。它要做的是把“当前执行位置、栈帧、作用域”逐一映射到 VS Code 的按钮和面板。你会发现每个界面动作都只是第一阶段某个概念的可视化操作。
