# 第九章：断点、单步与 Watch 的使用策略

## 承接前面三章：工具齐了，但问题还没有变小

第六至八章分别解决会话、变量和求值。如果没有策略，它们很容易变成一种低效习惯：在入口按 Step Into，一路跟进框架和依赖，半小时后忘记最初要查什么。

本章开始要求你先写假设，再放断点。断点的价值不在于“看到代码运行”，而在于它能用一次暂停区分至少两种可能。例如在 Service 入参正确、出参错误，就能把搜索边界缩到 Service 内部；如果入参已经错误，应转向上游。

学完后，你要能为同步故障写一份最多三个观察点的计划，并说明每个观察结果如何改变下一步。

### 纸上推演

假设订单最终金额错误，路径只有“输入解析 → 折扣计算 → 响应格式化”。你只有两个断点额度。先写下放在哪里，以及四种观察组合分别说明什么，再阅读 9.8 的二分定位。

## 9.1 断点应该回答问题

差的断点策略是在几十个函数入口都放红点，然后不断 Continue。好的断点对应一个可证伪的问题：

- 请求进入 Controller 时 `id` 是否已经错误？
- Service 返回前，错误值第一次出现了吗？
- 缓存命中时是否错误地跳过数据库？
- 循环处理第 37 项时，哪个字段违反约束？

先写问题，再选能区分两种答案的位置。

## 9.2 普通断点

适合低频路径和第一次理解代码。常放在：

- 输入刚进入系统的边界；
- 数据转换前后；
- 分支判断前；
- 外部 I/O 调用前后；
- 返回值形成前；
- 统一错误处理器之前（同时追溯更早抛出点）。

不要只在最终报错行暂停。错误值可能早在十层调用之前就产生了。

## 9.3 条件断点

在循环或高频请求中，只为目标情况暂停：

```js
item.id === 'u-42'
index === 36
user == null
total < 0
```

条件在被调试进程上下文求值。复杂条件可能拖慢热路径，也可能因 getter/函数调用产生副作用。尽量使用短、纯、不会抛错的判断。

## 9.4 Hit Count 与 Triggered Breakpoint

Hit Count 用于“第 N 次才出错”的路径；具体表达方式由调试器实现决定。Triggered Breakpoint 会在另一个断点先命中后才启用，适合“完成某个前置动作之后才观察”的故障。

它们是在减少噪音，不是在解释原因。命中后仍要检查输入、状态和调用链。

## 9.5 Logpoint

Logpoint 不暂停程序，而向 Debug Console 输出消息，可嵌入 `{expression}`。适合：

- 高频路径抽样；
- 暂停会破坏时序的问题；
- 不想修改源文件时收集值；
- 比较多个请求的关键字段。

它仍会求值表达式并带来性能开销。不要在表达式中执行写操作，也不要输出密码、token、Cookie、身份证号等敏感信息。

## 9.6 异常断点

Breakpoints 面板通常可选择：

- 在未捕获异常处暂停；
- 在已捕获异常处也暂停。

未捕获异常适合常规故障。已捕获异常能发现“底层先抛错，后来被统一处理器包装/吞掉”的源头，但框架可能大量使用内部异常控制流，噪音会很大。可以结合 `skipFiles`、条件和调用栈筛选。

Promise rejection 可能通过异步机制表现；优先在 rejection 的原始创建/抛出位置暂停，并保留 async stack trace。

## 9.7 Watch 表达式

Watch 在每次暂停时重新求值，适合持续比较：

```js
items.length
index
items[index]?.id
cache.has(key)
expectedTotal - actualTotal
```

坏的 Watch：

```js
items.shift()
service.save(user)
JSON.stringify(hugeGraph)
```

前两项修改状态，第三项可能昂贵、失败或触发自定义序列化。Watch 数量越多，每次暂停成本越高；故障结束后清理。

## 9.8 二分定位执行区间

当数据经过十个阶段后出错，不必逐行跟到底：

1. 在第 1 和第 10 阶段观察，确认输入正确、输出错误；
2. 在第 5 阶段观察；
3. 若第 5 阶段已错，检查 1～5；否则检查 6～10；
4. 重复缩小到第一次从正确变错误的位置。

这就是对控制/数据流做二分。它比无目标 Step Into 更快，也更容易留下证据。

## 9.9 调试一行多个调用

若 Step Into 总进入错误函数：

- 直接在目标函数第一条可执行语句下断点；
- 使用 inline breakpoint（调试器支持时）；
- 暂时把表达式拆为多个有名字的步骤；
- 配置 `skipFiles` 跳过 Node 内部或依赖代码。

拆分后不仅更好调试，也常常让错误处理和测试更清楚。

## 9.10 第二阶段综合练习

调试 `labs/01-sync-order-bug/app.js`。限制自己最多设置三个断点，回答：

1. 错误值第一次出现在哪一行之后？
2. 是输入、转换、分支还是最终格式化的问题？
3. 哪个条件断点能只暂停失败订单？
4. 修复后用什么输入防止回归？

完成后再看 `answers/01-sync-order-bug.md`。

## 第二阶段过关标准

你能清楚区分 Step Over 与“不执行”，能说明每次表达式求值属于哪个栈帧，能用不超过三个有目的的断点找到同步数据首次出错的位置。

## 第二阶段交接：从一个文件进入项目

到这里，单文件同步调试的基本能力已经闭环。第三阶段开始，状态不再只存在当前文件：一个模块会导出对象并被其他模块缓存，一份 Redis client 会被多个调用者共享，一个 `await` 会让同步栈断开。

这些不是推翻前面的模型，而是在其上增加边界。第十章先只增加“文件边界”，暂时仍保持同步。你将看到为什么 `require()` 第二次不再执行顶层代码，以及所谓单例为什么必须带上“在哪个进程内”这个限定。
