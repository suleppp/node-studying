# 附录：章末“停止阅读检查”参考答案

先独立口述，再核对关键词。答案不是需要背诵的标准句式；只要机制、边界和因果关系准确即可。

## 第一章

1. 两次启动是不同进程，各自有独立地址空间和 V8 状态；源文件相同不等于运行时变量共享。
2. 当前 shell 先解析命令、空格、引号和重定向，再请求操作系统启动 Node。
3. 仍有会保持事件循环活跃的 timer、server、socket 等资源时，入口末尾执行完进程也不自然退出。
4. V8 是 JavaScript 引擎；Node 在它周围提供模块、文件、网络、进程、libuv 和原生绑定等运行时能力。

## 第二章

1. 从项目根运行子目录入口时最常见：`cwd` 是项目根，`__dirname` 是入口/当前模块目录。
2. CommonJS 用模块包装形成模块作用域；文件通过 `module.exports` 明确共享值，而不是共享全部顶层绑定。
3. 未初始化的 `let`/`const` 访问会抛 `ReferenceError`；已初始化为 `undefined` 的绑定可正常读取，值就是 `undefined`。
4. 不能。`--check` 检查语法；文件是否存在通常要等相应运行路径执行 I/O 才知道。

## 第三章

1. 源代码行是显示单位，不是必然的最小执行单位；一行可有多个属性访问、调用、短路与副作用。
2. 左侧词法绑定已经建立但初始化尚未完成，不应说它已经等于 `undefined`。
3. 路径未到达、条件短路、连错进程、跑了另一个文件/旧构建、断点未绑定、source map 错或热重载换进程等。
4. Debug Console 在目标进程求值；重复调用函数、赋值或 getter 会改变后续状态，使证据失真。

## 第四章

1. 每次调用有独立帧，因此递归或重入时同一函数可以同时出现多层，每层参数/局部值不同。
2. 不会。点击只是选择要查看的活动帧，没有把程序时间倒退，也没有恢复已退出的帧。
3. 不一定；`try` 中 return 以后仍先执行 `finally`，而 `finally` 还可能替换结果或抛错。
4. 调度函数通常早已返回，真实同步帧已弹出；调试器显示的 async stack 是额外因果信息。

## 第六章

1. 不会。Step Over 只是不进入被调函数观察，它仍真实运行并产生副作用。
2. 当前函数可能抛错并转到 catch；`finally` 也可能改变控制流，因此不保证正常返回位置。
3. Variables、Watch、源代码位置、悬停求值与 Debug Console 上下文都会跟随所选帧。
4. 固定输入和工作目录才能建立可重复实验，避免把运行条件变化误判为代码变化。

## 第七章

1. 作用域决定名字在源位置是否可见；可达性决定对象是否仍能从活跃根被引用并影响回收。
2. 返回的内层函数仍引用外层词法环境，相关数据仍可达；外层活动栈帧已经退出不改变这一点。
3. 不同。声明执行前在 TDZ；`let x;` 执行完成后已初始化为 `undefined`。
4. 它只验证“若状态不同，后续会怎样”，没有修复产生错误状态的代码/配置，重启后也不会保留。

## 第八章

1. 活动调试会话中的 Debug Console，因为调试器能在当前暂停、所选栈帧上下文求值。
2. 属于 REPL 那个独立 Node 进程，不属于被调试应用进程。
3. 不一定。getter 本身是函数，可以修改内存、I/O 或抛错。
4. Debug Console 的 internal console 不提供应用所需的交互式标准输入；集成终端承载真实进程 stdin。

## 第十章

1. 相对 `require` 从发起加载的模块目录解析；普通相对文件 I/O 常从 `process.cwd()` 解析。
2. `exports` 起初只是指向 `module.exports` 的局部快捷引用；重新给它赋值不会替换 `module.exports`。
3. 解析到不同文件、不同 Node 进程、worker、不同加载机制或人为清缓存时，都可能有多份。
4. 为完成加载环，加载器必须先暴露尚未执行完的模块对象，所以另一方可能只看到当时已有的部分属性。

## 第十一章

1. connected 可能只表示底层连接建立；ready 可能还要求认证、握手、选库或初始化完成，实际定义看客户端。
2. 最终 client 在 await 完成前仍为空；共享 in-flight Promise 才能阻止并发调用同时建立多个连接。
3. `null` 是精确 miss 信号；真假判断还会误伤空字符串、`0`、`false` 等合法值。
4. 不总是。性能缓存可降级；锁、限流、会话、幂等键等正确性依赖失败时继续可能更危险。

## 第十二章

1. Promise 构造器 executor 在构造时同步执行；`.then` handler 被排入微任务，等当前同步栈完成后执行。
2. 不是。暂停的是该 async continuation；其他事件循环任务仍可在合适时机运行。
3. 不会。`Promise.all` 自己会拒绝，但已启动任务需要单独的取消协议，例如 AbortSignal。
4. 二者处于不同事件循环阶段，先后受注册上下文和当前循环状态影响；入口顶层一次观察不是普遍保证。

## 第十三章

1. 响应耗时受调度、系统负载和模拟延迟等影响；应通过 repository 断点、命令计数或 trace 证明是否访问 Mongo。
2. 第一项是当前进程模块图中的对象身份，第二项是该对象的生命周期状态，第三项是缓存数据；其中一项正确不能推出其他两项正确。
3. 连接失败是依赖不可用，用户不存在是成功查询后的业务结果；混为 404 会隐藏故障并误导调用者。
4. GET、SET、DEL 若身份 schema 不同，删除的不是读取使用的条目，旧值仍会命中。

## 第十四章

1. `runtimeArgs` 交给 Node/运行程序，`args` 在 program 之后交给业务入口。
2. 普通相对 I/O 通常基于进程当前工作目录；CommonJS 的 `__dirname` 由当前模块绝对位置决定。
3. attach Stop 通常只是断开并让目标继续；launch Stop 通常终止由调试器创建的目标程序。
4. 调试器必须把源码位置映射到实际执行的生成代码；旧构建、错误 outFiles 或 map 路径会使源位置不存在。

## 第十五章

1. 最终加载业务入口的 Node 子进程；npm、shell、nodemon 通常只是启动或监控层。
2. 重启创建了新进程和新 V8/模块加载器，旧进程内存与 CommonJS 缓存不会继承。
3. 不共享。`child_process.fork` 创建独立 Node 进程，只额外建立 IPC 通道，并非复制共享 JS 堆。
4. Attach 停止可能只断开，nodemon 等父监控者还可能存活或再次拉起业务进程。

## 第十六章

1. 属性可以由 getter/Proxy 实现；读取会运行用户代码，因此可能改变状态或 I/O。
2. 被暂停 worker 不能处理请求和心跳，上游超时后重试，额外请求又加重堆积并可能触发重启。
3. 它支持或否定“若这个值改变则现象改变”的假设；没有证明错误值的来源已修复，也没有通过自然路径回归。
4. Inspector 允许客户端在目标进程上下文求值，能调用该进程已有权限可做的文件、网络和数据操作。

## 第十七章

1. 输入或环境不能重复时，修改前后可能不是同一实验，无法把结果变化归因于代码修改。
2. 下游可能一直容忍错误值，直到某行无法继续才抛错；根因应沿数据流回到第一次从正确变错误的位置。
3. 可证伪假设必须预测能否定它的证据，例如“GET 使用了错误 tenant key；若为真，actual key 与按输入构造的 expected key 不同”。
4. 原操作只证明一个样本；反事实与邻近路径证明根因机制被消除且 miss/hit、not-found、依赖失败等契约没有被破坏。

## 第十八章

1. 原工单缺少精确输入、时序、环境、期望契约和实际字段，不能形成可重复实验。
2. 第二次 GET 是旧值进入失败读取的边界；更新路径无失效是让旧值继续存在的根因。
3. 数据库更新调用返回 Grace，并且数据库状态/命令记录显示更新成功。
4. 再执行一次会新增命令、可能改变 TTL/连接/时序；对真实依赖还可能产生费用、锁或其他副作用。
5. 数据库成功而 DEL 失败、并发旧快照在 DEL 后重新 SET、滚动版本 key 不一致等仍需按一致性要求处理。
6. 测试若在未修复版本也通过，就没有证明它覆盖了故障机制，未来也无法阻止同类回归。
