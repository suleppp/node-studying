# 第十九章：结业项目——独立接手陌生 Node 服务

## 19.1 任务性质

结业项目位于 `labs/04-multitenant-cache-leak/`。这是故意保留的多租户缓存数据泄漏：两个 tenant 中都有 id 为 `u1` 的用户，第二个 tenant 的读取可能得到第一个 tenant 的用户。

这比“名字旧了”更严重，因为错误值跨越了租户边界。你不仅要让示例输出正确，还要证明隔离契约恢复，并说明已产生缓存如何处理。

本章只规定交付物和评估标准，不给逐步操作。卡住时可以按顺序使用文末提示，但每打开一层提示，都说明对应能力还需回到前面章节练习。

## 19.2 原始工单

> 测试同学说 beta 租户查询 u1 时偶尔显示 Ada，但 beta 的 u1 应该叫 Lin。第一次刷新更容易出现，重新启动后顺序又会变化。请尽快修一下。

不要直接搜索 `Ada` 或修改返回值。先把工单变成可判定命题。

## 19.3 你必须提交的八份产物

### 产物一：复现说明

包括环境、启动命令、输入顺序、期望、实际和复现频率。任何同事只按你的说明都应得到相同结果。

### 产物二：运行对象证明

记录 Node 版本、PID/PPID、入口绝对路径、cwd，以及数据库和缓存属于进程内模拟还是外部服务。说明为什么重启/顺序会影响现象。

### 产物三：边界图

至少包括：调用者、UserService、缓存、数据库。每条箭头标注 tenantId、userId、cache key、raw 值或 user 对象。

### 产物四：假设表

至少三个可证伪假设，每个包含预测证据和实际结果。不能只写“缓存 key 错了”一个答案。

```text
假设：
如果为真，应观察到：
观察点与方式：
实际证据：
结论：支持 / 否定 / 尚不足
```

### 产物五：首次偏离证明

明确区分：错误值在失败请求中第一次从哪个边界进入，以及产生这类错误的根因代码/设计在哪里。

### 产物六：最小修复

修复必须集中 key schema，不能在响应层按 tenant 名称硬编码纠正，也不能靠每次禁用缓存绕过。写明兼容或清理旧 key 的策略。

### 产物七：回归矩阵

至少包括：

- acme/u1 冷读与热读；
- beta/u1 冷读与热读；
- 相同 userId 跨 tenant 不碰撞；
- 相同 tenant 的不同 userId 不碰撞；
- not-found 不读取其他 tenant 数据；
- key 中特殊字符的允许/编码规则；
- 修复部署前存在的旧 key 怎样过期或清理。

### 产物八：PR/交接说明

按第十八章格式提交现象、根因证据、修复、验证和剩余风险。假设读者没有参与你的调试。

## 19.4 建议时间盒

第一次独立完成可使用 90 分钟：

| 时间 | 任务 |
|---|---|
| 0～10 分钟 | 固化工单与复现 |
| 10～20 分钟 | 确认进程、入口、环境 |
| 20～30 分钟 | 画边界和列假设 |
| 30～50 分钟 | 最小观察，找首次偏离 |
| 50～65 分钟 | 设计并实现最小修复 |
| 65～80 分钟 | 回归矩阵 |
| 80～90 分钟 | PR 说明与剩余风险 |

时间盒不是要求仓促猜测。如果 20 分钟仍未稳定复现，应停在复现阶段，不要通过改代码制造一个看似正确的结果。

## 19.5 评分标准

总分 100：

| 维度 | 分值 | 满分标准 |
|---|---:|---|
| 复现质量 | 15 | 输入、顺序、期望、实际可由他人重复 |
| 运行对象 | 10 | 入口、PID、cwd、状态范围有证据 |
| 边界与假设 | 20 | 图清楚，至少排除两个合理错误假设 |
| 根因证明 | 20 | 找到首次偏离，命令/key/raw 数据完整 |
| 修复设计 | 15 | 单一 key schema，考虑旧 key 与隔离契约 |
| 回归覆盖 | 15 | 跨租户、同租户、not-found 和边界输入 |
| 交接表达 | 5 | 同事能快速复核且风险不被隐藏 |

达到 80 分并且“根因证明”“修复设计”均不低于各自一半，才算通过。只改对一行但没有证据和回归，最高不超过 50 分。

## 19.6 分层提示

### 提示一：只在无法稳定复现时阅读

运行顺序本身是输入的一部分。先读取 acme/u1，再读取 beta/u1，保存两次 source 和 cache 命令。

### 提示二：只在不知道观察什么时阅读

为两次调用建立表格，分别记录 `tenantId`、`userId`、GET key、raw、是否访问数据库。寻找两次请求中不应该相同却相同的字段。

### 提示三：只在知道问题但不会设计修复时阅读

缓存身份必须覆盖数据库查询身份的全部隔离维度。如果数据库由 `(tenantId, userId)` 唯一定位，缓存 key 不能只表达其中一维。GET、SET、DEL 必须调用同一个 key 构造函数。

完整参考答案位于 `answers/04-multitenant-cache-leak.md`。在八份产物写完前不要打开。

## 19.7 口头答辩

完成代码后，不看笔记回答：

1. 为什么现象依赖请求顺序，而不是真的“随机”？
2. 模块缓存、业务缓存和数据库身份分别是什么范围？
3. 哪条证据证明数据库中的 beta/u1 本身没有写错？
4. 为什么清空所有缓存只能缓解，不能修复？
5. 新 key 发布后，旧 key 会造成哪些兼容/容量问题？
6. 如果多个服务版本滚动部署，新旧 key schema 同时存在会怎样？
7. 哪些调试表达式是只读且足以证明问题的？
8. 如何让同类数据隔离 bug 在代码进入运行环境前被测试发现？

## 19.8 你现在达到的不是终点，而是工作起点

通过结业项目意味着你已经具备独立处理普通 Node 业务逻辑故障的工作框架：能确认运行对象、读同步和异步调用路径、跨模块追踪数据、观察缓存/数据库边界、控制调试风险，并用回归和交接完成闭环。

它不意味着你已经掌握所有专项问题。内存泄漏需要 heap snapshot，CPU 抖动需要 profile，分布式竞争需要 trace 与并发测试，原生崩溃可能需要 core dump。遇到这些问题时仍使用同一基础顺序：明确现象、确认对象、选择适合证据、验证假设、修复并回归。

以后学习新工具时，问的不是“这个按钮怎么按”，而是“它能提供哪一种证据、证据属于哪个运行对象、会不会改变被观察系统”。这就是本书希望留下的调试思维。
