# 第十七章：可复用的故障定位方法

## 前十六章终于要变成一种工作习惯

到目前为止，每章都在解决一个局部能力：理解进程、读调用栈、选择栈帧、追踪模块与 async、确认缓存事实、识别子进程并安全求值。如果这些能力只在相应示例里有效，你仍然不会调试陌生项目。

本章不再增加新的 VS Code 功能，而是规定使用这些能力的顺序。顺序非常重要：没有先稳定复现就修改，无法证明修复；没有先确认进程就下断点，证据可能来自错误实例；没有找到首次偏离就在响应层打补丁，根因仍会从别的路径泄漏。

学完后，你应该能把整个过程记录成别人可以复查的证据链，而不只口头说“应该是这里”。

### 先回忆一次自己的失败调试

想一个你曾经靠不断改代码解决的问题。写下当时是否保存了原始输入、是否知道错误值第一次出现的位置、是否排除过错误假设、是否有回归测试。读完本章后，用 17.1 的流程重新组织那次经历。

## 17.1 调试不是猜修复

成熟流程：

```text
明确现象 → 稳定复现 → 缩小边界 → 提出假设
    → 收集证据 → 找到首次偏离 → 最小修复 → 回归与复盘
```

每一步都有产物。没有复现条件，就不知道修改是否有效；没有首次偏离位置，就容易在下游症状处打补丁；没有回归，修复只是一次碰巧成功。

## 17.2 第一步：把“坏了”写成可判定命题

差描述：

> 用户接口不对。

好描述：

> 本地开发环境中，先请求 `GET /users/u1`，更新数据库名字后 1 秒内再次请求，响应仍返回旧名字；直接查数据库为新名字，响应元信息显示 cache。

它包含环境、输入、步骤、期望、实际和已知证据。

## 17.3 第二步：确认运行对象

在任何代码推理前记录：

```text
Node 版本：
启动命令/launch 配置：
PID/PPID：
入口绝对路径：
cwd：
代码提交/构建时间：
关键环境变量（脱敏）：
外部服务环境（local/test/...）：
```

大量“断点失效”和“修复没用”其实是运行错文件、旧构建、错误工作目录或另一个进程。

## 17.4 第三步：画边界，不画所有细节

以请求为例：

```text
HTTP 输入 | Controller | Service | Cache | Repository | DB
```

在每个边界记录输入/输出和异常。先判断错误跨过哪个边界后出现，再深入那一层。外部系统边界还记录超时、重试和请求 ID。

## 17.5 第四步：提出能被否定的假设

差假设：

> Redis 有问题。

可验证假设：

> 更新路径写数据库成功后没有删除 `user:u1`，所以第二次读取命中旧缓存。

证据预测：数据库记录新、Redis 原始值旧、更新路径命令日志无 DEL。只要看到 DEL 成功且之后又有旧 SET，这个假设就被否定并转向并发覆盖。

每轮保留 1～3 个假设，按“最能区分且成本最低”的证据验证。

## 17.6 找第一次偏离，不只找崩溃点

假设最终 `total` 为 -10。沿数据来源向前：

1. 响应格式化前是否已为 -10？
2. Service 返回是否为 -10？
3. Repository 数据是否正确？
4. 输入解析是否把折扣变为 110%？

第一次由正确变错误的位置最接近根因。最后抛 TypeError 的行有时只是第一个无法容忍错误值的位置。

## 17.7 选择合适工具

- 可稳定复现、低频同步路径：断点 + Variables；
- 第 N 次/特定输入：条件断点、Hit Count；
- 暂停会改变时序：Logpoint、结构化日志、trace；
- 跨异步请求：requestId、AsyncLocalStorage（真实项目）；
- CPU 慢：CPU profile，不靠逐行计时；
- 内存增长：heap snapshot、allocation profile、活动句柄；
- 多进程：PID/PPID、进程树、多目标调试；
- 外部依赖：客户端命令日志、服务端指标、超时与 trace；
- 生产环境：优先低侵入可观测性，不轻易暂停。

## 17.8 最小修复

修复应直接改变根因机制。例如 key 构造错了，就修复并集中 key 函数；不要在响应层遇到旧值时强行覆盖。

最小不等于最少字符，而是：

- 影响范围清楚；
- 不夹带无关重构；
- 可以用一个或少量测试证明；
- 失败时容易回滚；
- 对并发、错误路径和生命周期仍成立。

## 17.9 回归要覆盖反事实

修复 cache key 后至少验证：

- 原失败输入现在正确；
- 不同 tenant 不互相读到数据；
- 第一次 miss 和第二次 hit 都正确；
- not-found 行为不变；
- Redis 故障策略仍符合设计；
- 进程重启后行为一致。

回归不是“再点一次刚才按钮”，而是证明根因被消除且邻近契约没有破坏。

## 17.10 复盘模板

```text
标题：一句话描述故障机制
影响：用户/数据/时间范围
触发条件：最小输入与环境
时间线：发现、缓解、修复
根因：错误状态第一次产生的位置及机制
为什么未提前发现：测试/监控/评审缺口
修复：代码与配置变化
验证：自动测试和现场证据
预防：类型、契约、监控、文档或架构措施
```

避免把“某人粗心”当根因。追问为什么系统允许一个常见错误无测试、无约束、无告警地进入运行环境。

## 17.11 陌生项目的前 20 分钟

1. 读 `package.json` scripts 和入口；
2. 查看 Node/包管理器版本约束；
3. 还原实际启动命令和进程树；
4. 找配置加载点和 `cwd` 假设；
5. 找请求/任务入口、错误处理和依赖创建；
6. 正常运行一次保存基线输出；
7. 用最小输入复现；
8. 在第一个业务边界设断点，不先钻 framework internals；
9. 沿数据边界二分；
10. 形成证据链后才修改。

## 停止阅读检查

1. 为什么不能稳定复现时，修改前后的“成功”没有证明力？
2. 报错行与错误状态第一次形成的位置为什么可能不同？
3. 什么叫可证伪假设？请为“Redis 有问题”改写一个例子。
4. 为什么回归要覆盖修复机制的反事实和邻近路径，而不只重复一次原操作？

## 第四阶段过关标准

你能面对由 npm/监控者启动的多进程项目，证明自己调试的是正确 PID、入口和构建；能选择低风险观察手段，找到错误状态首次出现的位置；能给出最小修复与自动回归证据。

## 从“知道方法”到“完成工作”

方法清单很容易看懂，真正困难的是在信息不完整、时间有限、代码陌生时仍按顺序执行。下一章模拟一张真实故障工单：产品描述含糊、系统存在 Redis 与 Mongo、第二次读取返回旧值。你要看到一名开发者怎样从接单、澄清、复现一直走到可合并修复。

第十八章是带讲解的完整示范；第十九章会拿掉大部分提示，让你独立完成同样的交付。
