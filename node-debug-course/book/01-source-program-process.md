# 第一章：源代码、可执行文件与进程

## 本章在全书中的位置

这是全书唯一不要求任何调试知识的一章。我们先故意不打开 VS Code Debugger，因为如果连“谁正在运行”都没有分清，之后看到的断点、变量和调用栈就没有归属。

想象一个最常见的误会：你修改了 `app.js`，但终端中的服务行为没有变化。初学者容易继续检查那几行代码；工作中的第一反应应该是：当前提供服务的到底是不是读取这份文件的那个进程？这个问题的答案来自程序、可执行文件与进程的区分。

学完本章，你应该能完成三件事：

1. 从 `node app.js` 画出 Shell、操作系统、Node 可执行文件、进程和源码的关系；
2. 解释两次运行相同文件为什么仍有两份独立状态；
3. 判断“入口代码结束”与“进程结束”为什么不是同一件事。

## 1.1 磁盘上的 `app.js` 不会自己运行

```js
const a = 10;
const b = 20;
console.log(a + b);
```

保存以后，`app.js` 首先只是文件系统中的一串字节。编辑器按照 UTF-8 等字符编码把字节显示成 `c`、`o`、`n`、`s`、`t` 等字符。此时：

- 没有名叫 `a` 的运行时绑定；
- 没有值为 `10` 的 JavaScript Number 存在于某个 Node 进程中；
- 没有调用 `console.log`；
- 没有调用栈，也没有事件循环。

文本“描述”了将来可能进行的计算，但文本不是那次计算。

## 1.2 `node` 本身也是磁盘上的程序

命令：

```bash
node app.js
```

并不是让操作系统直接理解 JavaScript。Shell 先解析命令，寻找名为 `node`（Windows 通常是 `node.exe`）的可执行文件，然后请求操作系统启动它，并把 `app.js` 作为命令行参数传给它。

第一层模型如下：

```text
终端中的 shell 解析命令
        ↓
操作系统加载 node 可执行文件
        ↓
操作系统创建 Node.js 进程
        ↓
Node.js 根据参数找到并读取 app.js
        ↓
模块加载器包装并执行入口模块
        ↓
V8 解析、编译并执行 JavaScript
```

“Node.js 读取文件”和“V8 执行 JavaScript”中间还有模块解析、包装、语法分析、字节码/机器码生成等步骤。第二章会展开。

## 1.3 程序、进程和线程不要混在一起

**程序（program）**常指磁盘上的可执行内容和相关文件。**进程（process）**是程序的一次运行实例，是操作系统管理资源和运行状态的单位之一。

连续启动两次：

```bash
node app.js
node app.js
```

可以产生两个独立进程。即使代码、参数完全相同，它们通常也有不同的 PID（进程标识符）、地址空间、堆、句柄和生命周期。一个进程中修改的普通 JavaScript 变量，不会自动修改另一个进程的变量。

进程不是“只有一块内存”。对调试有用的简化内容包括：

- 自己的虚拟地址空间；
- 已加载的代码和共享库；
- JavaScript 堆及 V8 内部状态；
- 一个或多个操作系统线程；
- 打开的文件、网络连接、管道和定时器等资源；
- PID、环境变量、当前工作目录、命令行参数；
- 退出码和当前运行/等待/终止状态。

Node.js 执行用户 JavaScript 通常以一个主线程为中心，但“Node 只有一个线程”并不准确。V8、libuv 和某些 I/O/原生工作会使用其他线程。重要的是：普通 JavaScript 回调不会任意同时在同一个主线程栈上执行；它们要等事件循环调度。

## 1.4 Node.js 和 V8 的边界

V8 是 JavaScript 引擎，负责 JavaScript 的解析、编译、执行、对象内存管理和垃圾回收等。Node.js 把 V8 嵌入自己的运行时，并提供服务器和命令行程序需要的能力。

```js
const total = 10 + 20;           // JavaScript 语义主要由 V8 实现
console.log(total);              // console 由运行环境提供
const fs = require('node:fs');   // Node.js 模块系统和内置模块
fs.readFileSync('data.txt');     // Node.js、原生层和操作系统共同参与
```

这个边界不是说某行只能属于一方，而是帮助定位问题：语法、闭包、对象等问题通常从 JavaScript/V8 模型思考；路径、文件、网络、进程、模块解析等问题通常还必须考虑 Node 运行时和操作系统。

## 1.5 进程为什么会结束，为什么有时不结束

入口文件的最后一行执行完，不等于进程必然立即退出。Node.js 会在没有更多需要保持活动的工作时自然退出。下面的程序会继续存活：

```js
setInterval(() => {
  console.log('still alive');
}, 1000);
```

活动的定时器、监听中的服务器、某些 socket 等会让事件循环仍有工作。相反，只创建一个普通对象不会让进程永久存活。

退出方式包括：

- 自然退出：没有更多活动工作；
- `process.exitCode = 1`：设置最终退出码，让清理过程仍有机会进行；
- `process.exit(1)`：立即请求退出，可能来不及刷新异步输出；
- 未处理的致命错误；
- 操作系统或用户发送信号（例如终端中按 `Ctrl+C` 通常触发 SIGINT）。

调试“程序卡住”时，准确问题不是“最后一行是不是结束了”，而是“还有什么活动资源让进程保持存活”。

## 本章收束：给运行状态找到主人

现在再说“变量 `a` 的值是 10”，句子仍不完整。更准确的是：“PID 为某个值的 Node 进程，在执行这份入口模块时，某个作用域中的绑定 `a` 当前保存 10。”后面不必每次说这么长，但脑中必须保留进程这个主人。

本章只解释了操作系统怎样创建 Node 进程，还没有解释 Node 如何从命令行参数找到 `app.js`、为什么顶层变量不会自动变成全局变量、语法错误为什么能在第一条日志之前阻止执行。这正是第二章的任务。
