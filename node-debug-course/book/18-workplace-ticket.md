# 第十八章：从故障工单到可合并修复

## 18.1 这一章不再按知识点讲

前十七章把机制和方法分别拆开。本章换一种写法：按照工作中的时间顺序，完整跟踪一张故障工单。从你第一次读到产品反馈开始，到复现、观察、定位、修复、回归、提交说明结束。

示例使用 `labs/03-service-stale-cache/`。即使你已经做过这个实验，也不要跳过。过去的目标是找到 bug；现在的目标是交付一份同事可以审查、测试可以证明、上线风险可以讨论的修复。

## 18.2 你收到的原始反馈

工单只有一句话：

> 用户修改昵称以后，刷新页面偶尔还是旧昵称，重启服务后似乎恢复。

这句话不能直接拿来调试，因为至少有五处模糊：

- “修改”请求是否真的成功？
- “刷新”发起了哪个读取接口？
- “偶尔”与时间、用户、实例或缓存命中是否有关？
- “旧昵称”来自浏览器、Node 内存、Redis 还是 Mongo？
- “重启恢复”重启了哪个进程，是否恰好等待到 TTL 到期？

工作中的第一步不是打开代码，而是把描述变成可判定命题。

## 18.3 把反馈改写为复现定义

与报告者确认或在日志中补齐以下信息：

```text
环境：本地 / 测试 / 生产副本
用户与租户：使用脱敏标识
写请求：方法、路径、关键输入、响应状态
读请求：方法、路径、与写请求的时间间隔
期望：写成功后的可见性契约是什么
实际：响应中哪个精确字段仍为旧值
频率：必现 / 首次 / 第二次 / 特定实例
相关 requestId：写与读分别是什么
```

在本实验中，将工单收敛为：

```text
给定数据库中 u1.name=“Ada”且缓存为空，
第一次 getById('u1') 返回 Ada 并回填缓存；
updateName('u1', 'Grace') 返回 Grace；
紧接着第二次 getById('u1') 仍从 cache 返回 Ada。
期望第二次返回 Grace。
```

这已经是可运行、可判断成功失败的实验。

## 18.4 建立未经修改的基线

先运行，不下断点，不改代码：

```bash
npm run lab:03
```

保存完整输出。基线的作用有三个：

1. 证明当前版本确实复现；
2. 保存原始命令时间线，避免调试暂停改变顺序后丢失现场；
3. 修复后可以用完全相同输入比较。

此时应记录而不是解释：

| 时刻 | 已知事实 |
|---|---|
| 第一次读取后 | 响应 Ada，source=database |
| 更新后 | updateName 返回 Grace |
| 第二次读取后 | 响应 Ada，source=cache |

“Redis 有问题”还不是事实，只是可能的解释。

## 18.5 先确认自己正在研究正确运行对象

在简单实验里这一步看似多余，但必须训练成习惯。记录：

```text
启动命令：npm run lab:03
Node 可执行文件：process.execPath
入口：process.argv[1]
PID / PPID：process.pid / process.ppid
工作目录：process.cwd()
代码版本：当前工作区状态或提交
外部服务：本实验为进程内 FakeDatabase/FakeCache
```

这里使用了第一、十四、十五章。如果真实服务有多个实例，还要让日志或响应标出 instance/PID，证明失败读请求由哪个业务进程处理。

## 18.6 不读实现细节，先画数据边界

```text
调用者
  │ id='u1'
  ▼
UserService.getById
  │ key='user:u1'
  ▼
FakeCache.get
  ├─ raw=null → FakeDatabase.findById → FakeCache.set
  └─ raw=JSON → JSON.parse → 返回

调用者
  │ id='u1', name='Grace'
  ▼
UserService.updateName
  ▼
FakeDatabase.updateName
```

画到这里已经出现一个值得验证的结构性问题：更新路径与缓存之间没有画出箭头。但图只是从阅读得到的假设，不能直接当结论；实现可能通过 Repository 事件或其他模块间接失效。

## 18.7 建立假设树

保留三个能够被证据否定的假设：

### 假设 A：数据库更新没有真正成功

预测：`updateName` 的返回或数据库内部记录仍是 Ada；第二次即使绕过缓存，数据库也返回 Ada。

### 假设 B：数据库已是 Grace，但缓存旧值没有失效

预测：更新返回 Grace；命令时间线在更新后没有 DEL/SET；第二次 GET 返回含 Ada 的旧 JSON，随后不访问数据库。

### 假设 C：更新和读取发生在不同状态实例

预测：写与读的 PID/client 实例不同，或 key/tenant/environment 不同；各自局部证据都可能“正确”，但不在同一状态空间。

假设的好坏取决于能否被否定。“可能是缓存”太宽泛，任何结果都能硬解释，不能指导观察。

## 18.8 用三个观察点区分假设

不要从入口逐行进入。设置三个有职责边界的断点：

1. `UserService.updateName` 中数据库 await 完成后：观察 `updated` 和精确 id；
2. 第二次 `getById` 中 cache await 完成后：观察 key 与原始 `raw`；
3. 数据库 `findById` 入口：判断第二次读取是否真的到达主存储。

如果需要只在第二次读取暂停，可以使用 Hit Count，或临时以明确的调用序号/请求 ID 作条件。不要把 `cache.get()` 再执行一次来“确认”，那会增加真实命令并污染时间线。

## 18.9 读取证据，而不是寻找符合直觉的画面

这三个观察点会得到：

```text
更新后：updated.name === 'Grace'
第二次读：key === 'user:u1'
第二次读：raw 包含 name='Ada'
第二次读：数据库 findById 断点不命中
命令日志：SET 之后没有 DEL，也没有新 SET
```

据此：

- 假设 A 被否定：数据库更新返回了 Grace；
- 假设 C 在本实验被否定：所有状态都在同一进程、同一对象实例；
- 假设 B 得到支持：旧值从第二次 cache GET 边界重新进入 Service。

注意两个不同位置：

- **错误状态重新进入本次读取的位置**：第二次 `cache.get` 返回；
- **造成它仍存在的根因位置**：更新数据库后没有使相同 key 失效。

只在读取路径遇到 Ada 时强制改成 Grace，是在症状处修补。

## 18.10 设计最小修复前先写契约

这个项目采用 cache-aside，并把数据库当主存储。更新契约写成：

```text
数据库更新成功 → 删除对应缓存 key → 后续读取 miss → 读新数据库值并回填
```

因此最小修复是在数据库成功更新且用户存在后，删除由同一个 key 函数生成的条目：

```js
const updated = await database.updateName(id, name);
if (updated !== null) {
  await cache.del(this.key(id));
}
return updated;
```

这段代码很短，但评审不能只看 happy path，还要问：

- 数据库成功、DEL 失败时调用者得到成功还是失败？
- 若返回失败，数据库已经提交，重试会怎样？
- 两个并发读写是否可能把旧快照重新回填？
- TTL 多长，旧数据风险能否接受？
- 是否需要重试、版本化、消息/outbox 或更强一致性方案？

课程实验接受同步 DEL 作为最小修复；真实系统必须按业务一致性要求回答这些问题。

## 18.11 回归不是只重跑失败步骤

至少覆盖一张行为矩阵：

| 场景 | 期望 source/行为 | 证明的契约 |
|---|---|---|
| 冷缓存读取存在用户 | database，随后 SET | miss 路径 |
| 再次读取 | cache，不再 find | hit 路径 |
| 更新已有用户 | DB 更新后 DEL | 失效路径 |
| 更新后读取 | database，新值 | 原故障修复 |
| 读取不存在用户 | null，不误返回其他用户 | not-found |
| DEL 失败 | 按设计告警/失败/重试 | 依赖失败策略 |
| 并发读写 | 结果符合一致性约定 | 竞争边界 |

原故障用例必须先在未修复代码上失败，再在修复后通过。否则可能只是写了一个永远通过、没有覆盖根因的测试。

## 18.12 形成可合并的交付说明

一份合格的提交或 PR 描述可以是：

```text
现象：更新 u1 名称后，下一次读取命中旧缓存。

根因：UserService.updateName 只更新数据库，没有删除 getById 使用的
user:${id} cache-aside 条目。命令时间线显示 SET 后无 DEL，第二次 GET
直接返回旧 JSON，数据库读取未发生。

修复：数据库成功更新后，用统一 key 构造函数删除条目，使后续读取从数据库回填。

验证：新增冷读、热读、更新后读取、not-found 和 DEL 失败测试；原复现
在修复前失败、修复后通过。

风险：数据库提交后 DEL 仍可能失败；本次沿用项目现有依赖失败策略，另建任务
评估重试/事件化失效。并发旧值回填风险未由本最小修复完全消除。
```

这份说明允许评审者检验你的推理，不需要相信“我调过了”。

## 18.13 这一工单使用了前面哪些章节

- 第一、十四、十五章：确认入口、PID、工作目录与进程实例；
- 第三、四、六章：理解 await 前后的当前源位置和栈帧；
- 第七、八章：在正确帧安全读取 key、raw 和 updated；

- 第十章：确认 Service 和调用者共享哪个 cache 实例；
- 第十一章：区分连接状态、key、原始缓存值和解析值；
- 第十二章：理解 await 恢复与异步请求交错；
- 第十三章：沿 Service/Cache/Repository/DB 画数据路径；
- 第十六章：避免重复执行命令污染外部状态；

这就是“环环相扣”的最终意义：工作故障不是某一章的题，而是前面模型的联合应用。
